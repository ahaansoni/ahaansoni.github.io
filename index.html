Two systems I've worked on recently that I keep coming back to. Both anonymized no client name, no specific business context. The interesting part is the pattern, not the product.

Invalidating cache across N pods, the boring way

distributed state · kafka
The problem

A backend service is running on multiple pods behind a load balancer. Each pod caches user-permission data in its local Redis to avoid hitting the database on every request. When an admin updates a user's permissions in the database, the change needs to propagate to every pod, immediately, without taking the system down or restarting anything. Manually flushing each pod is fragile; restarting is overkill. The cache needs to invalidate itself.

The approach

An internal endpoint, resetGlobalUserPermission, kicks off the flow. The pod that receives the request does two things in sequence: flush its own local Redis cache for the user-details service, then emit a Kafka event with its own pod identity stamped into the payload. Every other pod is subscribed to that topic and consumes the event but the emitting pod skips its own message by comparing the event's pod identity to os.hostname(). No infinite loops, no duplicate work.

Each successful consume gets logged to Redpanda so the team can later audit: did pod B actually clear its cache? At what timestamp? That trail matters in a regulated environment where "the permission *should* be revoked" isn't good enough — you need proof.

Flow
[ Admin updates user in DB ] │ ▼ [ Hits /resetGlobalUserPermission on Pod A ] │ ┌────────┴─────────┐ ▼ ▼ [ Pod A: clear [ Emit Kafka event: local Redis ] GLOBAL_USER_PERMISSION_RESET_EBI payload = { podName: 'pod-a', ... } ] │ ┌─────────────────┼─────────────────┐ ▼ ▼ ▼ [ Pod B consumes ] [ Pod C consumes ] [ Pod A consumes ] │ │ │ skip? podName skip? podName skip? podName matches mine? matches mine? matches mine? → YES, skip │ │ clear local Redis clear local Redis │ │ ack → Redpanda ack → Redpanda
What I'd watch out for

Kafka is eventually consistent. There's a window maybe a few hundred milliseconds where Pod B is still serving the stale cached permission while Pod A has already cleared it. For permissions specifically, that's a real concern: a revoked user might still get through on one pod for a brief moment. The right hardening is a version stamp on the cache key, so even a stale cached value can be invalidated by comparing versions on read. Solving the "fan-out" was the first problem; tightening the consistency guarantees is the next one.

A config file is a programming language

config-driven platforms
The problem

In a large enterprise platform, business teams ship dozens of customer-facing journeys a year new service requests, new flows, new validations. The naïve answer is "write code for each journey." That doesn't scale. Every flow needs validation, external API calls, fulfillment logic, and notifications afterward. If every new flow needs a new pull request, a new deploy, and a new test cycle, the platform becomes the bottleneck.

The approach

A single journey lives as one large JSON configuration document easily 1,500-2,000 lines for a complex one. The engine that interprets it runs each journey through three execution phases:

┌──────────────────────────────────────────────────────────┐ │ PHASE 1 · pre-validation │ │ • Call external APIs (e.g. fetch product details) │ │ • Map query parameters from the agent's input │ │ • Run validation rules against the response │ │ → If any rule fails, abort. Journey doesn't proceed. │ └──────────────────────────────────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────┐ │ PHASE 2 · pre-execution │ │ • Call the fulfillment API (the actual business action) │ │ • If primary fails, fall back to secondary API │ └──────────────────────────────────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────┐ │ PHASE 3 · post-execution │ │ • Send communication (SMS / email / in-app) │ │ • Log to audit trail │ └──────────────────────────────────────────────────────────┘

The frontend config is part of the same document describing the dynamic form the agent sees: fields, sub-areas, prepopulation, attachments. Same source of truth for backend and frontend, which means a business change to "show this field only when X" is a config edit, not a code change.

What I worked on

I delivered a new end-to-end journey from scratch designing the configuration document for all three phases, authoring the validation rules, wiring up the external-API mappings, and shipping with audit traceability. Separately, I extended an existing journey to support multiple addresses and varied contact schemas authoring 1,900+ lines of DB configuration with zero application-code changes. New fields can be added later by editing the config; no deploy required.

The lesson

The interesting trade-off isn't "config-driven vs code." It's "where do you draw the line?" Putting too much logic in config makes the config itself a programming language one with no type system, no IDE, no debugger. Putting too little in config means every business change is an engineering change. The right line moved as the team matured and the tooling around it (schema validators, config linters, dry-run modes) is what makes the difference between "elegant" and "unmaintainable."

Updating 10,000 cameras without touching one

edge config · bandwidth-constrained
The problem

Cameras are mounted on commercial vehicles thousands of them, spread across the country. Each has ~190 config fields: zoom, resolution, frame dimensions, sensitivity thresholds, and so on. Settings change constantly as the product evolves. You obviously can't stop 10,000 vehicles and physically reconfigure each camera. And every camera runs on a SIM with limited, metered cellular data so whatever protocol you use has to be tiny on the wire.

The approach

When a camera boots (or receives a remote boot command), it serializes its current config to Protobuf chosen specifically because it's far more compact than JSON, which matters when you're paying per byte over cellular — and publishes it to a RabbitMQ queue. The backend consumes the message, deserializes it, and reconciles it against the desired config in MongoDB.

[ Camera boots ] ──► serialize config to Protobuf │ (compact — SIM bandwidth is metered) ▼ [ RabbitMQ queue ] ──► [ Backend consumer ] │ ▼ deserialize camera config │ convert DB config → Protobuf too (faster to diff in the same format) │ ┌───────────┴───────────┐ ▼ ▼ no difference fields differ → do nothing → keep DB values (source of truth), send only the changed fields back │ ▼ [ Camera applies, emits "config updated" event ]
Why it's only the changed fields

Sending the full 190-field config back every time would waste bandwidth and risk overwriting fields the camera legitimately owns. So the reconciliation diffs the two Protobuf configs, keeps the DB as the source of truth for managed fields, and ships only the delta. The backend team drives all of this through a REST CRUD API I built they create, read, update, and delete configs per customer account, and the next time the relevant cameras check in, they converge.

The lesson

The interesting constraint here wasn't compute, it was bandwidth. Designing for a metered SIM forces decisions you'd never make on a fat pipe: binary serialization over human-readable JSON, diff-and-send-delta over send-everything, pull-on-boot over constant polling. Constraints make the design.
